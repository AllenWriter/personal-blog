皆さん、こんにちは。乔です。

以前は開発者向けサービスに関わっていて、技術ドキュメントやツール関連の仕事もしてきました。だからずっと、ある一つの問いを気にしてきました。

**開発者ツールは、いつ本当に生産性を持つのか？**

「使える」ようになったときではなく、**安定して仕事を代行してくれる**ようになったときです。

今日は、最近ずっと試行錯誤している構成を紹介したいと思います。

**AI エージェントをクラウドホスト上のコンテナ化されたデスクトップ環境に置き、コードを書くだけでなく、リモート操作員のように継続的に働けるようにする。**

少し回りくどく聞こえるかもしれませんが、核心は一文で覚えてもらえれば十分です。

> **AI エージェントに本当に仕事をしてもらうなら、コマンドラインだけを渡してはいけません。ワークベンチを渡す必要があります。**

そして、そのワークベンチは、クラウドにあるのが最適です。

## 一、まず結論：なぜエージェントをクラウドに置くのか？

エージェントを使って実際に物事を進め始めると、すぐに次のことに気づくからです。

それは「質問に答えるボット」ではありません。むしろ、**ツールを呼び出す実行者**に近いものです。

ターミナルを渡せば、コマンドを実行します。ファイルを渡せば、読み書きします。ブラウザを渡せば、ページをクリックし、画面を確認し、結果をチェックします。権限と環境を渡せば、どんどん完成度の高いワークフローを代わりに完了してくれます。

すると、問題は次のようになります。

**こういうものは、どこで動かすべきなのか？**

多くの人が最初に思い浮かべるのは、ローカルのパソコンでしょう。しかし、ローカルのパソコンは実はあまり向いていません。

なぜか。

ローカルのパソコンは、電源が切れ、スリープになり、ネットワークが切れ、自分自身にも作業を中断されるからです。さらに重要なのは、次の点です。

- ローカル環境は雑然としている
- 個人のアカウントがたくさんある
- 仕事のファイルがたくさんある
- システムは大切なものだ

メイン機の上で、エージェントに自由に動き回らせたいとは、おそらく思わないでしょう。

ですから、より良い選択肢は多くの場合こうなります。

**クラウドに専用のマシンを用意し、エージェント専用の作業環境を与える。**

この利点は、とても現実的です。

### 第一に、より安定する

多くのエージェントのタスクは、ネットワークに依存しています。

- 依存関係の取得
- モデルへの接続
- Webサイトへのアクセス
- API の呼び出し
- 自動化処理

これらは、ローカルで動かすとネットワークや環境の問題で詰まりがちです。しかし安定した Linux のクラウドホストで動かせば、経路はずっとスムーズになります。

### 第二に、長時間の運用に向いている

多くのタスクは、5分で終わるものではありません。

たとえば、

- 定期的な巡回チェック
- 長時間にわたる Web ページの収集
- SNS の継続的な監視
- 情報の自動集約
- 一定間隔での管理画面の変更確認

こうしたタスクは、ローカルのパソコンで長期間安定して管理するのは難しいものです。クラウドホストは、まさにそのために存在しています。

### 第三に、より安全

エージェントをメインの開発機に直接置くと、境界がかなり曖昧になります。しかしクラウドホストに置き、さらにコンテナによる隔離という一層を加えれば、境界ははるかに明確になります。

- 何に触れられるか
- 何に触れてはいけないか
- タスクが失敗したときにどう回収するか
- 環境が汚れたときにどう作り直すか

これらすべてが、ずっと扱いやすくなります。

ですから、クラウドホストは「より高性能なローカルのパソコン」ではありません。むしろ、次のようなものです。

**エージェントに仕事をさせるための、専用のホスト環境。**

## 二、では、なぜ GUI が必要なのか？コマンドラインだけでは足りないのか？

これは、多くの人が最初に抱く疑問です。

> AI はコードを書けるし、コマンドも実行できる。それで十分ではないのか？ なぜデスクトップが必要なのか？ なぜ GUI が必要なのか？

現実のタスクの多くは、純粋なコマンドラインのタスクではないからです。

コマンドラインが担当するのは、

- インストール
- 設定
- スクリプトの実行
- ファイルの処理
- サービスの起動

などです。もちろんこれらは重要です。しかし現実の世界には、コマンドラインだけでは解決できないタスクがたくさんあります。

たとえば、

- Web の管理画面にログインする
- ページのボタンをクリックする
- ページが本当に正しく描画されたかを確認する
- ポップアップが表示されたかを見る
- 操作が本当に成功したのか、それともエラーだったのかを確認する
- 記録のためにスクリーンショットを撮る
- ページに変化があったかを観察する

こうしたことは、ターミナルだけでは足りません。

ですから、私は次の一言がとても気に入っています。

> **コマンドラインが答えるのは「実行できるかどうか」、GUI が答えるのは「人間のように操作できるかどうか」。**

これは二つの異なるレベルの話です。

エージェントにターミナルだけを渡すと、それはコマンドを打てる人のようなものです。しかし、そこにデスクトップ、ブラウザ、ウィンドウシステムを加えると、本物のリモート操作員に近づきます。

この違いは非常に大きいのです。多くの場面で必要なのは、「答えを計算すること」ではありません。次のことをしてほしいのです。

- 見に行く
- クリックする
- 確認する
- スクリーンショットを撮る
- 痕跡を残す
- 振り返る

このときに、GUI の価値が出てきます。

## 三、だから私が本当に欲しいのは、クラウドホストではなく「クラウド上のリモートワークベンチ」

ここまでくれば、概念を一つにまとめることができます。

私たちが欲しいのは、単なるクラウドホストではありません。欲しいのは、

**クラウド上にあり、リモートからアクセスでき、エージェントの作業に適したデスクトップ環境。**

それには、いくつかの条件が必要です。

- ブラウザがある
- デスクトップがある
- ターミナルがある
- リモートからアクセスできる
- スクリーンショットが撮れる
- 継続的に動かせる
- そして、隔離・複製・回収ができる

ここまで来ると、もはや「ソフトウェアを一つ入れる」という話ではないと気づくはずです。欲しいのは、完全な作業環境なのです。

そのため、最終的に選んだのは「システムに重いデスクトップを直接入れる」方法ではなく、次の方法でした。

**Docker で軽量なデスクトップコンテナを動かし、VNC / noVNC 経由でリモートアクセスする。**

すべての用語を深く説明する必要はありません。専門知識のない人向けには、次のように言い換えれば十分です。

> **サーバーに派手なデスクトップを入れているわけではありません。エージェントに、標準化され、リモートから接続でき、いつでも作り直せるワークベンチを届けているのです。**

それで十分です。

## 四、なぜ重いデスクトップシステムをまるごと入れず、軽量なデスクトップを選んだのか？

ここは簡潔に話せばよく、深入りしすぎないほうがいいところです。

聴衆は、GNOME と Xfce の歴史にそれほど関心があるわけではありません。彼らが知りたいのは、**なぜそれを選んだのか**、ということです。

答えはシンプルです。見た目がいいからではなく、安定して仕事をさせたいからです。

エージェントにとって大事なのは、デスクトップがかっこいいかどうかではありません。大事なのは、

- ブラウザが開けるか
- ページが描画されるか
- リモート接続がつながるか
- スクリプトが安定して実行できるか
- リソース消費が大きすぎないか

です。

ですから、私は軽量な方式に寄せています。理由は一言に集約されます。

> **コンテナの中でデスクトップを動かすとき、私たちが求めるのは豪華さではなく、信頼性です。**

## 五、この話の背後には、より大きな問題がある：AI コーディングで競われているのは、もはや「コードが書けるかどうか」ではない

このテーマで最も価値のある部分は、デプロイのコマンドではなく、この認識の転換だと思っています。

今日、多くの人が AI コーディングについて話すとき、関心はまだ次のようなことに向いています。

- モデルがどれだけ強いか
- 補完がどれだけ速いか
- 書かれたコードが人間っぽいか

しかし、エージェントに本当に仕事を任せ始めると、すぐに次のことに気づきます。

**生産性を決めるのは、モデルだけではなく、システムである。**

つまり、本当に重要になる問いは、次のようなものになっていきます。

- 環境をどう構築するか
- ツールをどう与えるか
- 権限をどう管理するか
- ワークフローをどう設計するか
- 失敗したときにどう巻き戻すか
- 結果をどう記録に残すか
- タスクをどう継続的に動かし続けるか

ですから、AI コーディングはエンジニアリングの複雑さを消し去ったわけではありません。複雑さが「手でコードを書くこと」から「システムを設計すること」へと移っただけなのです。

この一文は、ぜひ言葉にして伝えてください。

> **AI コーディングは、エンジニアリングの難しさを下げたわけではありません。難しさを「コードを書くこと」から、「エージェントが安定して働けるシステムを設計すること」へ移したのです。**

## 六、では、どうやってデプロイするのか？今は一つのコマンドで環境全体を立ち上げている

ここまで来れば、実際の操作に入るのは自然です。

もし試してみたい方がいれば、私が今使っているプロジェクトは **remote-claw** といいます。その役割は「ツールを一つ入れること」ではありません。

**一つのコマンドで、リモートからアクセスできるエージェントの作業環境を届けること。**

リポジトリのアドレスは次のとおりです。

```
https://github.com/TencentCloudADP-DevRel/remote-claw
```

中心となるコマンドは次のとおりです。

curl -fsSL https://raw.githubusercontent.com/TencentCloudADP-DevRel/remote-claw/main/install-standalone.sh | sudo bash

このコマンドが裏で何をしているかを、話す際にすべての詳細を読み上げる必要はありません。三つの層として説明すればよいでしょう。

### 第一層：ホスト環境を準備している

たとえば、Docker、依存関係、実行条件などです。

### 第二層：リモートデスクトップのワークベンチを立ち上げている

ブラウザ、デスクトップ環境、リモートアクセス機能などを含みます。

### 第三層：エージェントに必要な基盤をまとめて起動している

この環境が、見るだけでなく、実際に仕事に使える状態になります。

ですから、このコマンドの本質は、

「ソフトウェアを一つインストールすること」

ではありません。

**リモートから操作でき、継続的に動き、エージェントが仕事をするのに適した標準環境を届けること。**

## 七、どんなシーンに最も向いているのか？

この部分は、しっかり絞り込む必要があります。3つ挙げれば十分で、聴衆がすぐにイメージできるものにしましょう。

### シーン一：Web の巡回チェックとプロダクトの検収

たとえば、

- 管理画面を開く
- ページにエラーが出ていないかを見る
- ボタンが存在するかを確認する
- 記録のためにスクリーンショットを撮る
- 巡回の結論を出力する

これまでこの種の作業は、人が手作業でクリックを繰り返すことが多くありました。今は、エージェントが一次チェックを行えるので、とても合っています。

### シーン二：Web ページと SNS の継続的な監視

たとえば、

- 定期的にページを開く
- キーワードの変化を見る
- スクリーンショットを記録する
- 新しい内容をまとめる
- 日報を生成する

この種の作業は、クラウドで長期間動かすのに特に向いています。ローカルのパソコンでは、このリズムに耐えられません。

### シーン三：コンテンツ処理と資料の整理

たとえば、

- 文字起こし後のテキストの整形
- 複数の素材の集約
- Web コンテンツの抽出
- 初稿の整理
- 構造化された出力

このシーンは非常に実用的です。なぜなら、人々が AI を「チャットボット」として捉える認識から、「ワークフローアシスタント」として捉える認識へ、すぐに切り替えられるからです。

さらに、次の一言を添えてもよいでしょう。

> **以前は AI を質問応答のツールとして使っていました。これからは、実行環境を持つワークフローのノードとして捉えるべきです。**

## 八、最後にどうまとめるか？

今日お伝えしたかったのは、デプロイコマンドそのものだけではありません。三つの判断です。

**第一に、エージェントは単なるチャットツールではない。作業環境が必要である。**

**第二に、クラウドホスト＋コンテナ＋GUI によって、エージェントは本当のリモート実行者に近づく。**

**第三に、AI 時代の開発者にとって最も重要な能力は、ますます一行一行のコードを手で書くことではなく、エージェントが継続的に働けるシステムを設計することになっていく。**

もし後で自分で試してみたいなら、GitHub のリポジトリに直接アクセスして、まずこの環境を立ち上げてみてください。本当に大事なのは「入れられたかどうか」ではなく、それを何度も再利用できるワークフローに変えられるかどうかです。

ありがとうございました。
