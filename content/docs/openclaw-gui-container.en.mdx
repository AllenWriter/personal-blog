Hello everyone, I'm Qiao.

I used to work on developer services, and I've also done technical documentation and tooling work, so I've always been focused on one question:

**When does a developer tool become truly productive?**

Not when it merely "works," but when it starts to **steadily get work done for you**.

Today I want to share a setup I've been tinkering with lately:

**Put an AI agent inside a containerized desktop environment on a cloud host, so it's not only able to write code, but can also keep working like a remote operator.**

It sounds a bit convoluted, but you can remember the core idea in one sentence:

> **For an AI agent to really get work done, you can't just give it a command line. You have to give it a workbench.**

And that workbench is best off in the cloud.

## I. First, the conclusion: why put the agent in the cloud?

Because once you really start using an agent to get things done, you quickly realize:

It isn't a "Q&A bot." It's more like an **executor that calls tools**.

Give it a terminal, and it runs commands. Give it files, and it reads and writes them. Give it a browser, and it clicks through pages, looks at them, and checks the results. Give it permissions and an environment, and it can complete increasingly complete workflows for you.

So the question becomes:

**Where should this kind of thing run?**

Many people's first instinct is their local computer. But a local computer isn't really a good fit.

Why?

Because your local machine shuts down, sleeps, loses its network connection, and gets interrupted by you. And more importantly:

- Your local environment is messy
- You have lots of personal accounts
- You have lots of work files
- Your system is valuable

You probably don't want an agent roaming freely on your main machine.

So a better choice is often:

**Give it a machine in the cloud, and give it a dedicated working environment.**

The benefits of this are very practical:

### First, more stable

Many agent tasks depend on the network:

- Pulling dependencies
- Connecting to models
- Accessing websites
- Calling APIs
- Running automation

These things often get stuck on network and environment problems when run locally. But on a stable Linux cloud host, the path runs much more smoothly.

### Second, better for long-running work

Many tasks don't finish in five minutes.

For example:

- Scheduled inspections
- Long-running web scraping
- Continuous monitoring of social media
- Automatically summarizing information
- Checking a backend periodically for changes

Those are hard for a local computer to host stably over long periods. A cloud host is built for exactly that.

### Third, safer

If you run an agent directly on your main development machine, the boundaries are quite blurry. But if you put it on a cloud host and add another layer of container isolation, the boundaries become much clearer:

- What it can touch
- What it must not touch
- How to clean up if a task goes wrong
- How to rebuild if the environment gets dirty

All of these become much easier to handle.

So a cloud host isn't a "fancier local computer." It's more like:

**A host environment dedicated to letting agents work.**

## II. Why do we still need a GUI? Isn't the command line enough?

This is the question many people ask first:

> AI can write code and run commands. Isn't that enough? Why give it a desktop? Why a GUI?

Because many real tasks aren't pure command-line tasks.

The command line handles:

- Installation
- Configuration
- Script execution
- File processing
- Starting services

Those matter, of course. But in the real world, there's a huge pile of tasks the command line simply can't solve.

For example:

- Logging into a web admin backend
- Clicking page buttons
- Checking whether a page actually rendered successfully
- Seeing whether a pop-up appeared
- Confirming whether an action truly succeeded or threw an error
- Taking screenshots for records
- Watching a page for visual changes

Terminal alone isn't enough for those.

That's why I especially like this line:

> **The command line answers "can it be executed," while the GUI answers "can it be operated the way a human does."**

Those are two different levels.

If you only give an agent a terminal, it's like a person who can type commands. But if you add a desktop, a browser, and a window system, it becomes much closer to a true remote operator.

That difference is huge. In many scenarios, you don't want it to just "calculate an answer." You want it to:

- Go look
- Go click
- Go confirm
- Go take a screenshot
- Go leave a trace
- Go review

That's where the value of a GUI comes in.

## III. So what I really want isn't a cloud host, but a "remote workbench in the cloud"

At this point, you can pull the concept together.

What we want isn't simply a cloud host. What we want is:

**A cloud-based, remotely accessible desktop environment suited for agent work.**

Ideally it has a few things:

- A browser
- A desktop
- A terminal
- Remote access
- Screenshot capability
- Continuous operation
- And the ability to be isolated, copied, and reclaimed

At this point, you realize you're no longer just "installing some software." You're after a complete working environment.

Because of that, the option I ended up choosing isn't "install a heavy desktop directly on the system," but:

**Run a lightweight desktop container with Docker, and access it remotely through VNC / noVNC.**

You don't need to explain every term in depth. For a non-technical audience, you can translate it into plain language:

> **I'm not installing some fancy desktop on a server. I'm delivering a standardized, remotely accessible, rebuildable workbench for the agent.**

That's enough.

## IV. Why choose a lightweight desktop instead of a full heavy desktop system?

This part can be simple, and shouldn't go too deep.

Because the audience doesn't necessarily care about the history of GNOME and Xfce. What they care about is: **why did you choose this?**

The answer is simple: I'm not doing it to look good. I'm doing it to get work done reliably.

For an agent, what matters isn't how flashy the desktop is, but:

- Can the browser open?
- Do pages render?
- Can remote access connect?
- Can scripts run stably?
- Is resource usage too high?

So I lean toward a lightweight solution. The reason boils down to one line:

> **When running a desktop in a container, we're after reliability, not luxury.**

## V. Behind all this is a bigger question: in AI coding, the competition is no longer about "can it write code"

I think the most valuable layer of this talk isn't the deployment commands, but this shift in understanding.

Today, when people talk about AI coding, their attention is still on:

- How strong the model is
- How fast completion is
- Whether the code looks like a human wrote it

But once you really start letting agents do real work, you'll quickly find:

**What determines whether it's productive isn't just the model, but the system.**

In other words, the questions that really matter become:

- How the environment is set up
- How tools are provided
- How permissions are managed
- How workflows are designed
- How to roll back when something goes wrong
- How results are recorded
- How tasks keep running continuously

So AI coding didn't eliminate engineering complexity. It simply moved complexity from "writing code by hand" to "designing a system."

You have to say this one out loud:

> **AI coding didn't make engineering difficulty go down. It moved the difficulty from "writing code" to "designing a system where agents can work stably."**

## VI. So how do you deploy it? I'm currently using a single command to bring up the whole environment

Now that we've covered the concepts, getting into the hands-on part is easy.

If you want to try this, the project I'm using right now is called **remote-claw**. Its purpose isn't "installing a tool," but:

**One command that delivers a remotely accessible agent working environment.**

The repository address is:

```
https://github.com/TencentCloudADP-DevRel/remote-claw
```

The core command is:

curl -fsSL https://raw.githubusercontent.com/TencentCloudADP-DevRel/remote-claw/main/install-standalone.sh | sudo bash

When you present this, you don't need to recite every detail of what the command does. You can explain it in three layers:

### Layer one: it prepares the host environment

For example, Docker, dependencies, and runtime requirements.

### Layer two: it brings up the remote desktop workbench

This includes the browser, the desktop environment, and remote access capability.

### Layer three: it starts the infrastructure the agent needs

So the environment can not only be seen, but actually used to get work done.

So the essence of this command isn't:

"Installing a piece of software."

It's:

**Delivering a standard environment that can be operated remotely, runs continuously, and is suited for agents to get work done.**

## VII. What scenarios suit this setup best?

This section needs to be tight. Three examples are enough, and each should let the audience immediately picture it.

### Scenario one: web inspection and product acceptance

For example:

- Open the backend
- Check whether the page shows any errors
- Check whether the buttons are there
- Take screenshots for records
- Output an inspection conclusion

In the past, this kind of work was often manual clicking. Now the agent can do the first pass, which is a very good fit.

### Scenario two: continuously monitoring web pages and social media

For example:

- Open pages on a schedule
- Check whether keywords have changed
- Record screenshots
- Summarize new content
- Generate a daily report

This kind of task is especially well suited to long-running work in the cloud. A local computer can't handle that rhythm.

### Scenario three: content processing and material organization

For example:

- Cleaning up transcribed text
- Summarizing multiple pieces of material
- Extracting web content
- Organizing first drafts
- Structured output

This scenario is very practical, because it lets people immediately shift from thinking of AI as a "chatbot" to thinking of it as a "workflow assistant."

You can even add one sentence:

> **We used to treat AI as a Q&A tool. Now we should treat it as a workflow node with an execution environment.**

**Third, the most important ability for developers in the AI era is less and less about hand-writing every line of code, and more and more about designing a system that lets agents keep working.**
